# grid_tools - insurer grid -> portal rate-config upload CSV

**Start with `AGENT_CONTEXT.md` and `MASTER_SCHEMA.md`** (the logic of every upload column, given by the user for the maintaining agent; where the scripts' conventions differ from its wording they are deliberate - do not 'fix' them). `AGENT_CONTEXT.md` is the whole system in one file (rules, the 42-column contract, master lists, workflow, pattern and failure catalogues, insurer playbooks, decision log, the self-learning
protocol) and the skill `.claude/skills/grid-converter/` (the procedure; `scripts/learn.py` records lessons, regression cases and knowledge-file updates). After every grid, run the learning protocol
(AGENT_CONTEXT.md section 12). This file stays the current-state reference for each script.
**One skill per insurance company** (the user, 4 Nov 2026: "creating a skill insurance company wise, for our agent to understand"): `.claude/skills/<insurer>-grid/SKILL.md` for `shriram`, `sbi`, `icici`, `liberty`, `magma`, `rsa` (both RSA scripts), `united`, `godigit`, `indusind` (the insurer = the first word of the script's file name) - load it TOGETHER with `grid-converter` before you ask the user anything:
its Status, **Rules the user has set (do not re-ask)**, Traps seen, Open items and Monthly procedure are the short memory of that insurer, with `AGENT_CONTEXT.md` section 7 and the decision log as the long record. After every run that taught something about an insurer, add it with
`python .claude/skills/grid-converter/scripts/learn.py skill --insurer <x> --section status|rules|traps|open --text "..."` (a rule the user gives goes into the skill AND the decision log); a new script gets its skill in the same job (`tests/skills_tests.py` and `check_regressions.py` fail without it).
`grid-converter` also has **Job E** (the user sends the grid, your output and THEIR corrected export: find every hand fix, turn it into a rule - `grid-converter` section 5b, `AGENT_CONTEXT.md` 5.4).

**One dedicated reference per insurer** (the user, 23 Nov 2026: "each individual insurer has its own dedicated .md file and its own dedicated Skill file"): `<INSURER>_GRID.md` in this folder - `SHRIRAM_GRID.md`, `SBI_GRID.md`, `ICICI_GRID.md`, `LIBERTY_GRID.md`, `MAGMA_GRID.md`, `RSA_GRID.md` (both RSA scripts), `UNITED_GRID.md`, `GODIGIT_GRID.md`, `INDUSIND_GRID.md` - next to the skill `.claude/skills/<insurer>-grid/SKILL.md`. The `.md` is the full reference of that insurer's grid and script (the grid, how it becomes rows, names, notes, edge cases, how to check a run, the user's decisions, what is open); the skill is the short memory the agent loads first. Keep both true in the same job: edit the `.md`, then `learn.py skill`. `check_regressions.py` and `tests/insurer_docs_tests.py` fail when a converter script has no `<INSURER>_GRID.md` or its skill does not point at it.

**Documentation and skills are rule-based: no Excel cell references** (the user, 23 Nov 2026: "no hardcoded Excel cell references (specific row numbers or column letters) anywhere ... purely rule-based and logic-based so they remain reliable even if the Excel layout changes"). In any `.md` of the project (this file, `AGENT_CONTEXT.md`, `lessons_learned.md`, the insurer files, the skills) never write a cell address, a column range, a row number, a column letter or a code index: name a place in a grid by its LABELS (the words of a sheet's title, a header chain, a row's label) and by the RULE that finds it, and check a number by labels, not by address. `.claude/skills/grid-converter/scripts/cellref_lint.py` lists every such form; `learn.py` refuses text that holds one; `check_regressions.py` and `tests/insurer_docs_tests.py` fail on one.

## Notes the script cannot apply: the remarks column (standing rule from the user, all scripts)

The `remarks` column is already one of the 42 upload columns. A note or text rule that a script cannot turn into logic is

## Rules for any fix
1. **Read `lessons_learned.md` first.** The standing user rules at the bottom of it are not up for debate
   (DD/MM/YYYY dates, rates only from the grid, PO = PI - 7 floor 0, IRDA handling, fixed Pan India Private Car 27/25, ids, units).
2. **Never invent a rate and never ask the user for one.** If a number cannot be read from the grid, the script asks which
   column to use (or to write 0 / leave rows out) - it never guesses, and it never drops rows silently. A rule that only a NOTE
   states and the script cannot read is flagged in `remarks` (see above), not asked about.
3. **Turn ambiguity into a question, not a hard-coded guess.** Use the existing `Asker` (`ask.choose`, `ask.confirm`, `ask.decide`)
   with `short=`/`memo` so the same question is asked once per run. Find columns by header text (ignoring spaces and
   capitals via `label_key` / `slab_key`), never by position.
4. **Smallest change.** Edit the function that failed, not the whole file. Do not restructure or rename.
5. **All scripts share one block** (between the `# %% ---- QUESTIONS` and `# %% ---- READING THE ...` headings). Edit it in ONE
   script and run `sync_shared.py` so the others get the identical text; `check_regressions.py` fails when they differ
   (and run `tests/service_tests.py`: the web app depends on the service mode in that block).
6. **Back up before editing**: copy the script to `backups\<name>.<yyyymmdd-hhmm>.py` (this folder is not under git).
7. **Spot-check against the Excel itself**, independently of the script: pick 3-5 cells in the new grid with openpyxl and
   confirm the matching output rows carry the same rate (remember Liberty x100 and PO = PI - 7). Pick each cell BY LABELS - the row's label cell and the column's header chain, found by searching the sheet for those texts - never by a typed address: the next grid moves every address.
8. **Stop and ask the user** when a column's meaning is unclear, a sheet looks like a different product, row counts move by
   more than ~5% with no explanation in the layout diff, or the only way forward is a guess. A column that keeps a
   plausible name and number range but changes *meaning* cannot be detected by any script - say so when it is possible.
9. Never overwrite a file in `output\` the user may have uploaded already; write to `output\` with the script's own naming. Test suites must not write there either (F-58: the Colab-flow tests of the slow suites did, under the names of a real September / October run; they use a temp folder now): after running any suite check `find output -newermt <today>`.
10. After the user accepts: `grid_doctor.py snapshot`, add an entry to `lessons_learned.md`, and (with the user's OK) add the
    new grid to `regression\cases.json` (copy it into `regression\inputs\`) and `--bless`.

## Keeping token use low (this runs on a Pro plan)
Do not read a 1,400-line script top to bottom. `grep` for the function named in the error, read just that function.
Do not dump whole sheets; use `grid_doctor.py dump`, and read specific cells with openpyxl when needed.
Run `check_regressions.py` once at the end (about a minute), not after every edit; use `--only <case>` while iterating.
Before you call a change done: `check_regressions.py` says ALL OK and `tests/run_tests.py` passes (add `--all` if you touched the shared block).
